**Impact: Open gap.** Checking the 0.5.0 own-glibc packaging against what
the `dn-glibc` fused loader needs: the loader itself is covered (`libc6`),

## Context

The fused loader (`dn-glibc`) drops `ld-dn` and leans on glibc's own,
prefix-retargeted mechanisms: the shim loads from
`<prefix>/etc/ld.so.preload`, and libraries resolve from
`<prefix>/etc/ld.so.cache` (see `dl-mechanics.md`). The loader itself is
already our patched build; the question here is whether everything the
cache path needs is packaged.

## What the check found

- **Loader: covered.** `libc6-exact-out.deb` ships our patched
  `usr/lib/aarch64-linux-gnu/ld-linux-aarch64.so.1` (1.16 MB) plus the
  compat symlink. The loader is part of `libc6`, so it is our build.
- **`ldconfig`/`ldd`: not covered.** The real Debian `libc6` `.deb`
  contains **no** `ldconfig`/`ldd` (verified: `dpkg-deb -c` grep is empty);
  those are in the separate **`libc-bin`** package. Our own-glibc build
  *did* produce `usr/sbin/ldconfig` and `usr/bin/ldd` in its destdir, but
  `scripts/bootstrap/dn-package-glibc.sh` only repackaged **`libc6`** (and
  `libc6-dev`) -- `libc-bin` was left as Debian's, host-compiled build.

## Why it matters

`<prefix>/etc/ld.so.cache` is generated by `ldconfig`. Debian's `libc-bin`
`ldconfig` is compiled for the *host* `/etc`, so it cannot populate the
prefix's cache. Without a prefix-targeted `ldconfig`, the fused loader has
no env-free way to find the prefix's libraries (the proof so far used
`--library-path`, i.e. env). So `libc-bin` must be our build too.

## Fix

Repackage `libc-bin` the same way as `libc6`: take Debian's real `libc-bin`
`.deb` as the template, replace its payload (`ldconfig`, `ldd`, `locale`,
... -- whatever the package's manifest lists that own-glibc produced) from
the own-glibc destdir, keep Debian's control metadata. Then a prefix install
gets a prefix-targeted `ldconfig`, and `ldconfig` can write
`<prefix>/etc/ld.so.cache`. Tracked in `TODO.md`, "Runtime overhaul";
implementation follows this entry.
